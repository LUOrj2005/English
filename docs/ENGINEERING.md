# 词镜 WordLens · 当前用法评估与工程规范指南

> 适用对象：**只有自己使用**，电脑负责改功能 → 推送到 GitHub **公有仓库** → 平板 `git clone` 后运行；本机基本不产生学习数据。
> 编写日期：2026-11-06　|　配套文档：`README.md`
> 本文只做说明与建议，不代表代码已经按这些建议改造。哪些已经改了，见第 6 节。

## 0. 结论先行

1. **现在这套用法是成立的**，不用推倒重来：默认只监听 `127.0.0.1`（平板浏览器访问的是平板自己），密钥和数据库都没进仓库，代码量也不大，一个人用完全够。
2. **最影响体验的不是代码质量，是数据不跨设备**：`data/` 被忽略，平板的生词本、词卡缓存、对照历史、佳句库永远是空的，两台机器各学各的。词典文件已经随仓库同步了，但「导入」这个动作每台设备仍要做一次。
3. **如果哪天要上线给外人用，现有代码几乎每个"对外"的假设都要重做**：没有登录、没有速率限制、API Key 可被间接导向任意地址、单机 SQLite 没有多用户隔离。这不是"再加个密码"能解决的，需要按第 4 节分阶段做。
4. **工程规范不必一次做齐**。它解决的是三类具体问题：改错、泄密、换台机器跑不起来。对当前场景，先做「.gitignore 复核 + 配置模板 + 提交前语法检查」三件就够了。

## 2. 工程规范是什么（给不熟的人）

### 2.1 一句话

工程规范 = **一套让"三个月后的自己"和"别人"能安全改代码的约定**。它不是大公司的形式主义，只解决三件很实际的事：

- **改错**：改 A 弄坏 B 时，能很快发现、能退回上一个可用版本；
- **泄密**：密钥、个人数据不会因为一次疏忽被推到公有仓库；
- **换机器跑不起来**：新设备照着文档就能装好，而不是靠记忆。

### 2.2 七块积木（每块：是什么 → 本项目现状 → 最小做法）

| 积木 | 白话解释 | 本项目现状 | 最小做法 |
| --- | --- | --- | --- |
| **版本管理** | 每次提交是一个可回退的存档；提交信息让人事后能检索 | 14 次提交，信息如「平板长句无法阅读(4)」，能看懂但不好检索 | 用 `类型: 简述`，如 `fix: 平板长句朗读降级`、`docs: 补充佳句章节`；发版时打 tag（`v1.1.0`），维护 `CHANGELOG.md` |
| **仓库卫生** | 明确哪些东西**永远不进仓库** | `.gitignore` 已经覆盖密钥、数据、日志、依赖，做得不错 | 每次提交前 `git status`；装 `gitleaks` / 开启 GitHub Secret scanning 做自动扫描；`git ls-files` 定期复核 |
| **配置管理** | 配置和代码分开：代码公开，每台机器自己的值本地给 | `config.json` 明文存 Key，启动自动生成；网页还能改 `baseUrl` | 新增 `config.example.json`（只有字段名与占位值）；正式值用环境变量或本地文件；对外服务用密钥管理服务（如 Vault / 云厂商 Secrets Manager） |
| **依赖与运行环境** | 锁住"用什么版本跑"，避免换台机器就崩 | `package.json` + `package-lock.json` 已有；`node:sqlite` 是 Node 22 实验 API；两个可选依赖 | 加 `engines.node` 与 `.nvmrc`；`npm audit` 定期看漏洞；升级 Node 大版本前先在电脑上试跑 |
| **代码组织** | 一个文件只管一类事，同一段逻辑只写一遍 | `server.js` 约 1540 行、`app.js` 约 2160 行、`style.css` 约 1220 行；朗读逻辑在 `app.js` 与 `reader.js` 重复约 114 行 | 后端按 `routes / db / ai / tts / config` 拆模块；前端抽公共 `tts.js`；先拆最常改的那部分，不必一次拆完 |
| **质量保障** | 自动帮你检查低级错误；改动后有"冒烟测试"确认主要功能还活着 | 无 lint、无测试、无 CI | 先加 ESLint + Prettier；再给 `/api/tts`、`/api/dict`、`/api/dictionary/import`、`/api/documents` 写 4 个接口冒烟测试；最后用 GitHub Actions 在每次 push 时跑 `node --check` + lint + 测试 |
| **文档** | 让人不用读代码就知道怎么装、怎么用、怎么改 | README 342 行很详细，但曾与代码脱节（本轮已补） | README 只讲"安装 / 使用 / 常见问题"；细节放 `docs/`；改动写进 CHANGELOG；开源加 LICENSE |

> 名词解释：**lint** = 自动检查代码写法与潜在错误的工具；**CI** = 每次推送代码时自动在云端跑一遍检查；**冒烟测试** = 只验证"最主要的功能没坏"的一组小测试；**tag** = 给某次提交起一个版本号，方便随时回退。

### 2.3 不想折腾的话，先做这三件

1. `.nvmrc` + `package.json` 的 `engines.node`：把 Node 版本固定下来（Termux 升级后不会突然跑不起来）。
2. `config.example.json`：新设备照着填，不用翻源码找字段名，也避免误把真实 Key 写进模板。
3. 一个极小的 GitHub Actions：每次 push 跑 `node --check server.js public/*.js lib/*.js`，语法错当场拦下。

这三件加起来不到 30 行配置，却覆盖了「换机器跑不起来」和「改错」里最常见的两类事故。

## 3. 如果要上线：会有哪些问题、一般怎么解

### 3.1 先分清"上线"的三种档次

| 档次 | 含义 | 需要做多少 |
| --- | --- | --- |
| A. 自己远程访问 | 部署到一台云主机 / 家里 NAS，只有自己用 | 阶段 0 + 1，再加 HTTPS 与口令即可 |
| B. 给少数人用 | 同学、朋友也能访问，数据仍可各管各的 | 阶段 2：鉴权、限流、错误脱敏、备份、HTTPS |
| C. 面向公众的产品 | 不特定用户注册使用，可能收费 | 阶段 3：账号体系、多用户数据隔离、数据库迁移、配额、监控、合规 |

**别用 C 的标准吓自己**：你现在是"自己用 + 本机/平板"，连 A 都不算，下面大部分问题暂时不成立。

### 3.2 风险清单：本项目具体问题 → 业界一般做法 → 最小落地

| 类别 | 本项目的具体情况 | 风险 | 一般解决方案 | 在本项目的最小落地 |
| --- | --- | --- | --- | --- |
| **身份认证** | 所有 `/api/` 无鉴权、无 CSRF 防护、无速率限制；`host` 可设 `0.0.0.0` | 同网任何人可删库、改配置、刷 AI 接口 | Session / JWT / OAuth；RBAC 角色权限；网关限流；CORS 白名单 | 一个环境变量口令 + 一个中间件，对所有 `/api/` 校验；限流用简单的内存计数即可 |
| **密钥与 SSRF** | `POST /api/config` 可改 `baseUrl`，而 `chatCompletion()` 会把 `Bearer ${apiKey}` 发给这个地址；`/api/config` 本身也无鉴权 | 别人把地址改成自己的服务器，就能**收到你的 API Key**（SSRF + 凭证外泄） | 密钥放环境变量 / 密钥管理服务；出站地址白名单；配置接口加权限；密钥轮换机制 | 固定 `baseUrl` 白名单或只允许环境变量设置；给 `/api/config` 加口令；Key 用环境变量注入 |
| **输入校验** | `word` ≤120、`text` ≤300、请求体 1–40MB 不等，校验散落在各处理函数；错误直接回显 `err.message`；`/api/status` 返回数据库绝对路径 | 参数异常导致 500；内部路径 / 上游错误内容外泄 | 统一 schema 校验（zod / joi）；统一错误码与脱敏；限制 Content-Type 与文件类型 | 一个 `validate()` 小工具集中校验；全局 catch 对外部请求只返回通用提示，详细信息写日志 |
| **数据层与并发** | 单个同步 `DatabaseSync` 连接、WAL 模式、无 `busy_timeout`、无 schema 版本管理、无定时备份 | 多进程 / 多用户写入易锁；数据结构变更无迁移记录；硬盘坏了数据全丢 | Postgres/MySQL + 迁移工具（Prisma / Flyway）；连接池；定时备份 + 恢复演练 | 若仍是单人：保留 SQLite，但加定时复制备份、WAL checkpoint、schema 版本号表 |
| **多用户隔离** | 5 张表全是全局数据，没有 `user_id`，生词本 / 词卡 / 佳句库没有归属 | 一旦开放第二个人，互相看得到、改得到对方数据 | 用户表 + 所有业务表加 `user_id` + 查询强制带条件；行级权限 | 阶段 3 才做；阶段 2 若只是"几个人各用各的"，可以每人一个独立进程 + 独立数据库文件 |
| **传输与部署** | 纯 HTTP；无进程守护；端口占用自动顺延；日志只打印到终端 / `data/import.log` | 明文传输；服务崩了不会自动拉起；出问题没有记录可查 | 反向代理（Caddy / Nginx）+ Let's Encrypt 自动 HTTPS；systemd / pm2 守护；结构化日志 + 日志轮转；健康检查 | Caddy 一行配置自动 HTTPS；pm2 或 systemd 托管 `node server.js`；统一日志格式 |
| **AI 成本与滥用** | 无配额、无熔断；单次请求超时 180s；文档翻译并发 3 批；缓存按设备独立 | 一个脚本就能刷爆账单；上游变慢时请求堆积 | 每用户配额 + 服务端共享缓存 + 队列 + 超时/重试/熔断 + 账单告警 | 后台设置消费上限；给 `/api/ai` 加简单的每 IP 频率限制；共享词卡缓存 |
| **第三方依赖** | Edge TTS 硬编码 UA / GEC 版本；有道为非官方接口；`mammoth`、`anki-apkg-export` 为可选依赖 | 上游改协议即失效；供应链漏洞无人提醒 | Provider 抽象（可替换实现）；锁版本 + Dependabot；监控成功率；失败降级 | 把 Edge / 有道封装成可替换的 provider；依赖升级有记录 |
| **前端与 PWA** | 全量 `innerHTML` 渲染、无 CSP、SW 缓存版本号靠手改、图标按钮无 `aria-label` | 潜在注入面、缓存不更新、可访问性不足 | CSP 响应头；构建 + 带哈希的文件名；语义化标签与 ARIA | 先固定"改前端必升 `CACHE_NAME`"这条流程；给图标按钮补 `aria-label` |
| **可观测与应急** | 无错误上报、无指标、无备份回滚演练 | 出问题时只能靠用户描述 | 结构化日志 + 错误追踪（Sentry）+ 关键指标 + 回滚 tag | 至少把错误写到带时间戳的日志文件，并保留上一个可用 tag |
| **合规与内容** | 公有仓库无 LICENSE；词典来源未标注；AI 生成内容、学习数据属于个人信息 | 授权不清；若对外提供服务，涉及个人信息处理与内容责任 | 明确 LICENSE、词典来源与授权；隐私说明；对外服务遵循个保法 / GDPR | 加 LICENSE 与词典来源说明；若只自己用，至少别把 `data/` 公开 |

### 3.3 最容易被忽略的三个坑

1. **"明文存 Key"不是最危险的，"能改 Key 发往哪里"才是。** 只要有人能调用 `POST /api/config` 改 `baseUrl`，服务端就会带着 `Bearer Key` 去请求那个地址——等于把钥匙送到对方手上。修 Key 的存储方式之前，先锁住配置接口和出站地址。
2. **"加个登录"不等于"支持多用户"。** 登录只解决"谁能进门"，数据隔离要靠每张表都有归属字段、每条查询都带过滤条件。否则 A 用户在生词本里能看到 B 用户的记录。这个项目要走到这一步，5 张表都要改，属于阶段 3。
3. **AI 接口是"按次计费的公开入口"。** 本地工具没有配额无所谓，一旦放到公网，一个循环脚本就能产生真实账单。最低成本的保护是服务商后台的额度上限 + 服务端频率限制。

## 4. 怎么整理：分阶段路线

> 原则：**够用就好**。每阶段都写清"什么情况下才需要做"，避免为了规范而规范。

### 阶段 0 · 仓库卫生（现在，0 代码）

- **触发条件**：仓库是公开的、有多台设备 —— 已经满足，**应该做完**。
- 做的事：复核 `.gitignore`（已做）、确认历史无密钥（已做）、词典随仓库同步（已做）、README 与代码对齐（已做）、每台设备单独填 Key、两台设备记录 `node -v`、开启 Secret scanning / Dependabot、加 LICENSE 与词典来源说明。
- **验收**：`git status` 干净；`git ls-files` 里没有 `config.json` / `data/`；新设备照 README 能在 5 分钟内跑起来。

### 阶段 1 · 自己用得更顺（改动量：小）

- **触发条件**：你开始嫌"手动复制数据库 / 每次改前端要记得升版本号"麻烦。
- 做的事：`config.example.json`、`.nvmrc` + `engines`、`CHANGELOG.md`、一个 `update.sh`（git pull + 提示重启 + 提示升 SW 版本）、一个「导出 / 导入全库」按钮（解决第 1 条痛点）、GitHub Actions 跑语法检查与 4 个接口冒烟测试、后端按 `db / ai / tts / routes` 逐步拆模块。
- **验收**：换一台新电脑，clone → 填配置 → 导入备份 → 数据完整；push 后 CI 自动报告结果。

### 阶段 2 · 给第二个人用 / 公网自访（改动量：中）

- **触发条件**：需要在不可信网络访问，或有人跟你共用。
- 做的事：口令鉴权中间件 + 所有 `/api/` 校验；每 IP 频率限制；`baseUrl` 白名单、禁用或保护 `/api/config`；错误脱敏；Caddy/Nginx + HTTPS；pm2/systemd 守护；定时备份 `data/wordlens.db`；日志轮转；ESLint + Prettier 全量接入。
- **验收**：不带口令的请求全部 401；外部无法修改出站地址；服务异常退出能自动拉起；备份文件能成功恢复。

### 阶段 3 · 真正的产品化（改动量：大，几乎重写数据层）

- **触发条件**：不特定用户注册使用、需要付费或承诺可用性。
- 做的事：账号体系 + 权限；所有表加 `user_id` 与数据隔离；换 Postgres + 迁移工具 + 连接池；AI 配额与队列、熔断、账单告警；CI/CD 与回滚；监控告警、错误追踪；压测；隐私政策、内容授权、合规评估；前端工程化（构建、CSP、可访问性）。
- **验收**：多用户数据互不可见；有配额与告警；有备份恢复与回滚演练记录。

## 5. 检查清单（可复制）

**每次提交前**

- [ ] `git status` 里没有 `config.json`、`data/`、`.env`、`*.db`、`*.log`、`node_modules/`
- [ ] 提交信息是 `类型: 简述`，不含密钥、口令、私人邮箱
- [ ] `node --check server.js public/*.js lib/*.js` 通过
- [ ] 若改了 `public/` 下任何文件：`public/sw.js` 的 `CACHE_NAME` 已 +1
- [ ] README / CHANGELOG 是否需要同步（新增接口、新表、新依赖、新流程）

**每次推送给平板前**

- [ ] 电脑上服务能正常启动，至少点一次查词、一次句子朗读
- [ ] 新增 / 修改的词典格式仍是 `word / phonetic / senses[{pos, meaning}]`
- [ ] 平板 `git pull` → 重启服务 → 强刷浏览器 → 验证主要功能
- [ ] 词典若有更新，提醒自己在平板上重新导入一次

**真要上线前**

- [ ] 所有 `/api/` 都有鉴权；配置接口不能改 `baseUrl`
- [ ] 密钥来自环境变量或密钥管理服务，且最近轮换过
- [ ] 错误响应不泄露堆栈、绝对路径、上游原文
- [ ] HTTPS 生效；服务有守护进程；日志可查
- [ ] 有备份，并且**实际恢复过一次**
- [ ] 有速率限制 / 配额，服务商后台设了消费上限
- [ ] LICENSE、词典来源授权、隐私说明齐备
- [ ] 有一个可回退的 tag 与回滚步骤

## 7. 术语小词典

| 词 | 白话意思 |
| --- | --- |
| commit / tag | 一次存档 / 给存档起的版本号 |
| CI | 每次推送代码，云端自动帮你跑检查 |
| lint | 自动挑出代码里的写法问题和低级错误 |
| 冒烟测试 | 只验证"主要功能没坏"的几个小测试 |
| 环境变量 | 不写进代码、由运行环境提供的配置值（如 API Key） |
| 迁移（migration） | 数据库结构变更时，让旧数据平滑升级的脚本 |
| 幂等 | 同一个操作做一次和做多次，结果一样 |
| 速率限制 | 限制一段时间内某个来源能请求多少次 |
| SSRF | 诱导服务端去访问攻击者指定的地址，常用于窃取凭据 |
| 反向代理 | 挡在应用前面的服务器，负责 HTTPS、转发、限流等 |
| WAL | SQLite 的一种日志模式，`-wal` 文件里可能有尚未合并进主库的数据 |
| 回滚 / 熔断 | 退回上一个可用版本 / 上游持续失败时暂时不再请求，避免雪崩 |
| 依赖锁文件 | `package-lock.json`，记录每个依赖的确切版本，保证换机器装到的完全一样 |
